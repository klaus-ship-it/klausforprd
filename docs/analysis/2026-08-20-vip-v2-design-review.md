# VIP 機制 v2 設計覆核：盲點與缺陷

- 分析日期：2026-08-20
- 覆核對象：[docs/spec/vip-v2-spec.md](../spec/vip-v2-spec.md)、[docs/spec/vip-v2-tdd.md](../spec/vip-v2-tdd.md)、[docs/decisions/2026-08-20-vip-mechanism-redesign.md](../decisions/2026-08-20-vip-mechanism-redesign.md)
- 方法：逐條重新推演業務規則，對關鍵邏輯（晉升判斷）用腳本模擬實際跑一次以驗證，不是純人工推導

## 問題 1（嚴重／邏輯 bug）：降級機制形同虛設

### 現象

TDD [§3.1 checkPromotion](../spec/vip-v2-tdd.md) 的判斷邏輯是：只要玩家「終生累積儲值/流水」達到某等級的晉升門檻，就晉升到該等級。但終生累積數據**只會增加、永遠不會減少**（決策 D2 明確要求「不歸零」），而月底降級（§3.2）**不會**去動終生累積數據（決策 D2/D4 明確要求「降級不影響真實累積數據」）。

這代表：玩家一旦終生數據達到過 VIP5 的門檻，這個「達標」狀態會永遠成立，即使之後因為保級失敗被降到 VIP4，只要系統下一次執行晉升檢查（規格書寫的是「系統持續追蹤」，也就是玩家下一筆儲值或下注就可能觸發），會立刻重新判定「終生數據達到 VIP5 門檻」而把玩家打回 VIP5。

### 驗證

我用 TDD 虛擬碼原樣模擬了一次（腳本存於 [docs/decisions/vip_v2_demotion_bug_repro.py](../decisions/vip_v2_demotion_bug_repro.py)）：玩家終生儲值 9,000（VIP5 門檻 8,100）、當月保級沒過被降到 VIP4，下個月玩家隨便下一筆小注觸發檢查，結果 **判定應晉升回 VIP5**。降級的效果只維持到下一次系統檢查為止，實際上等於沒有降級。

### 這是哪裡漏掉的

舊版 `VIP.md`（規格書原文）其實有處理這個問題，用的是「情境 A / 情境 B 雙向邏輯」：
- **情境 A（首次晉升，目標等級 > 歷史最高等級）**：看終生累積數據 vs 晉升門檻
- **情境 B（降級後重升，目標等級 ≤ 歷史最高等級）**：改看「當月累積數據」 vs 該等級的**保級門檻**（門檻較低，且用當月數據不是終生數據），玩家必須重新證明「這個月夠格」才能重升

我們這次討論時（決策 D3 固定降 1 級、D4 防重複領獎）確認了「降級」和「防重複領獎」的規則，但沒有把「重新晉升時該用哪個門檻判斷」這件事單獨拉出來討論——結果簡化保級緩衝機制（把 Retention 數值扣減式緩衝改成布林保護期，這部分是刻意簡化，見決策紀錄）的同時，**連帶把「情境 A/B 判斷分支」也一起漏掉了，但這不是你要求拿掉的東西，是討論疏漏**。

### 建議修正方向

在 `checkPromotion` 裡加回這個分支：目標等級如果 ≤ 歷史最高等級（代表玩家以前到過，這次是降級後重升），要看「當月累積數據」是否達到該等級的**保級門檻**；只有目標等級 > 歷史最高等級（真正的生涯新高）才看終生累積數據 vs 晉升門檻。這樣才會讓 AC-3 驗收標準（降級後不會立刻重升）真正成立。

**這個修正會讓玩家體感變得更嚴格**（降級後真的要重新達標才能回去，不是我一開始以為的「純技術修正」），需要你確認是否接受這個體感，或是你其實想要的就是目前這種「軟性降級、稍微努力一下就能回去」的效果——如果是後者，那 checkPromotion 維持現狀反而是對的，但要把 AC-3 的敘述改掉，兩者只能選一個，不能又要 AC-3 成立又維持現在的判斷邏輯。

## 問題 2（中等）：多幣別流水如何折算成「終生累積流水」完全沒定義

現有 `Player.wallets` 是多個幣別並存（GOLD/SILVER/BRONZE，見 [src/types/player.ts](../../src/types/player.ts)），舊版 `VIP.md` 有特別註明「銀幣投注將依 100:1 折算後計入此門檻進度」。v2 的 `vip_lifetime_turnover` / `vip_current_month_turnover` 是單一數字欄位，但 spec/TDD 都沒交代這個數字是「只算金幣」還是「所有幣別折算後加總」，也沒說折算匯率跟 `RolloverEngine` 現有的 `exchangeCurrency()`（匯率 1:100）是否是同一套。這是一個會直接影響晉升門檻公平性的規格空白，不同幣別玩家的晉升速度會因為這個沒講清楚而產生實作歧義。

## 問題 3（中等）：升級獎勵卡與既有彩金佇列機制的排隊衝突沒設計

決策 D7 選擇復用現有 `BonusCard`/`RolloverEngine`（[src/mocks/engine.ts](../../src/mocks/engine.ts)）發放獎勵。但該引擎目前的設計是「同一時間只能有一張 active bonus card，其餘進 `bonus_queue` 排隊」（`tryActivateNext()`）。跨級晉升時（例如一次從 VIP1 跳到 VIP4）會一次產生好幾張 VIP 獎勵卡，加上玩家手上可能還有其他行銷活動發的彩金卡在排隊——這些卡片彼此的排隊優先順序、玩家能不能同時擁有多張排隊中的獎勵卡，目前完全沒有設計規則，實作時很可能會撞到既有系統的假設。

## 問題 4（中等）：P2P 贈禮手續費的計算方向沒定義

VIP 權益裡的「P2P 贈禮手續費」，規格書只寫了費率百分比，沒有寫**誰的等級決定費率**（贈禮方還是收禮方）、也沒寫**扣款基礎是贈禮金額還是其他**。P2P 轉帳一定牽涉兩個玩家，等級可能不同，這個方向性問題如果不先定義，工程實作時只能自己猜一個版本做，之後很可能要返工。

## 問題 5（中等）：稽核日誌沒有保留「當時的門檻版本」

[VIPAuditLog.snapshot](../spec/vip-v2-tdd.md) 只記錄玩家當下的儲值/流水/活躍天數快照，沒有記錄「判斷當下，這個等級的門檻設定值是多少」。如果營運之後調整了某等級的門檻數字，舊的稽核紀錄會沒辦法回溯查證「當初玩家到底有沒有達標」，一旦玩家對降級/未晉升有異議，客服/稽核會拿不出當時判斷依據的完整證據。建議 snapshot 裡也存一份「判斷當下使用的門檻值」。

## 問題 6（中等）：活躍天數的計算觸發時機沒定義

保級用的「當月活躍天數」定義是「當日有登入且當日有有效投注」（決策 D9），但沒定義這個計數器**什麼時候、由誰觸發 +1**——是玩家登入時檢查當天是否已下注過、還是每次下注時檢查當天是否已登入過、還是每日跑一次批次统一判定所有玩家。三種實作方式在「玩家先登入後幾小時才下注」這種常見情境下可能得到不同結果，需要明確定義，否則前後端容易對不齐。

## 問題 7（輕微）：等級「停用」狀態的行為沒定義

v2 新增了 `status: ACTIVE | INACTIVE`（對照落差報告問題 3 的修正），但停用一個等級後：
- 已經在這個等級上的玩家維持不動，還是要被強制調整？
- 晉升檢查（`checkPromotion` 的 for 迴圈）要不要跳過停用的等級？如果不跳過，玩家可能晉升到一個「已停用」的等級，這在營運邏輯上通常是不合理的
目前規格書和 TDD 都沒交代，這是一個具體的營運情境（例如要下架/重新設計某一級時）沒被想到。

## 問題 8（輕微）：反套利/防刷機制完全沒有討論

一次性升級獎勵最高到銀幣 75,000（VIP15 草案），加上 P2P 手續費折扣、投注返水，這幾項權益疊加後金額不小。舊版 `VIP.md` 對「儲值/流水的真實性」沒有太多著墨，v2 也一樣沒有討論：玩家之間互轉小號資金衝儲值數據、無風險對沖下注刷流水（等於是免費刷 VIP 等級和獎勵）這類手法，目前的門檻設計完全沒有防範。這不是這次討論範圍內的疏漏（原規格書本來就沒有），但既然是重新設計，建議至少列為已知風險，交由風控模組（Risk）評估是否需要額外規則。

## 問題 9（輕微）：「無獎勵」選項的型別語意不夠明確

`upgrade_reward_currency` 型別是 `'BRONZE' | 'SILVER' | undefined`，用 `undefined` 表示「無獎勵」。這會讓「忘記設定」和「故意設定無獎勵」在資料層面無法區分，儲存/驗證邏輯容易出現灰色地帶。建議型別明確加上 `'NONE'` 選項，而不是用空值表示。

## 優先順序建議

| 問題 | 嚴重度 | 建議處理時機 |
|---|---|---|
| 1. 降級形同虛設 | **高，邏輯 bug，會讓核心機制失效** | 規格書定案前必須先決定要不要修正，這是本次覆核最需要你拍板的一項 |
| 2. 多幣別流水折算 | 中，影響公平性 | 建議在數值草案定案前一併補上規則 |
| 3. 獎勵卡排隊衝突 | 中，影響上線後的實際體驗 | 可以在 TDD 定案時一併設計，不急著現在決定 |
| 4. P2P 手續費方向 | 中，實作歧義 | 同上 |
| 5. 稽核未存門檻版本 | 中，影響未來稽核完整性 | 建議定案時一併加入 |
| 6. 活躍天數觸發時機 | 中，前後端易對不齊 | 建議定案時一併加入 |
| 7. 等級停用行為 | 輕微 | 可以晚點補 |
| 8. 反套利機制 | 輕微但金額有感 | 建議交給風控模組評估，非本次必須解決 |
| 9. 無獎勵型別語意 | 輕微 | 可以晚點補 |

問題 1 是這次覆核最關鍵的發現，因為它直接影響整套機制「降級規則到底有沒有意義」，建議你先看這一項，決定要恢復原規格書的「情境 A/B」分支邏輯，還是接受目前這種「軟性降級」的效果並改寫對應的驗收標準。
