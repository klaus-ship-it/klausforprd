# 決策紀錄：VIP 機制重新設計

- 日期：2026-08-20
- 背景：既有規格文件 `VIP.md`（OPE-1002/1003/1004）與現有程式碼比對後（見 [docs/analysis/2026-08-20-vip-spec-vs-implementation.md](../analysis/2026-08-20-vip-spec-vs-implementation.md)）發現數值與實作大量脫節，Cooper 決定不修補、而是重新討論定義整套機制。本檔記錄討論過程中每一項架構決策、選擇的理由、以及放棄的替代方案。

## 決策清單

### D1. VIP 核心商業目標
- **決定**：雙軌並重（終生累積儲值 **AND** 終生累積流水都要達標才能晉升）
- **放棄方案**：純儲值驅動（只看課金）、純流水驅動（只看活躍投注）
- **理由**：延續規格書精神，避免只儲值不玩或只玩小注不儲值的極端用戶跳級，門檻更能反映真實貢獻度

### D2. 累積方式
- **決定**：終生累積（不歸零）
- **放棄方案**：週期累積（如每季重新歸零計算）
- **理由**：玩家不會因單月消費空窗就前功盡棄，晉升只會往上不會因不活躍而卡住；代價是資料模型需要另外維護「終生累積」與「歷史最高等級」兩組數據（見 D8 資料模型）

### D3. 保級失敗降級幅度
- **決定**：固定降 1 級
- **放棄方案**：直接降到「當期數據對應的等級」（可能一次跌好幾級）
- **理由**：規則單純、對玩家衝擊較溫和，避免因單月消費波動造成玩家大幅度跌等而流失

### D4. 降級後重升是否可重複領獎
- **決定**：不可重複領（需要防迴圈機制）
- **理由**：避免玩家刻意「衝等級 → 降級 → 重衝」刷一次性升級獎勵；代價是需要維護「歷史最高等級」+「該等級獎勵是否已核發」的紀錄（見 D8、D10）

### D5. 保級保護期
- **決定**：有，晉升當月不參與保級考核，下個月才開始計分
- **理由**：避免玩家月中才剛晉升，當月消費數據不足一整月自然偏低，卻立刻被下月結算判定降級

### D6. 獎勵結構範圍（本輪）
- **決定**：本輪只設計「一次性晉級獎勵」；週期性零用金、生日禮金、安慰金等規格書舊版曾提過的獎勵類型，列為之後另行討論的項目，不在這次的資料模型與畫面範圍內
- **理由**：先把核心晉升/保級引擎與一次性獎勵這個最基本的迴路設計完整，避免範圍一次鋪太大

### D7. 獎勵發放機制
- **決定**：復用現有 `BonusCard` / `RolloverEngine`（[src/mocks/engine.ts](../../src/mocks/engine.ts)）的資料結構與打碼流程，發放「VIP 升級銀幣獎勵卡」
- **放棄方案**：獎勵直接入現金錢包，不需打碼
- **理由**：與平台既有的彩金系統一致，不用重新發明一套獎勵流程，也維持「防套利」的打碼要求

### D8. 資料模型：新增欄位
承接 D2/D4/D7，玩家身上需要新增以下欄位（現行 `Player` 型別完全沒有）：
- `vip_lifetime_deposit` / `vip_lifetime_turnover`：終生累積儲值/流水（晉升判斷用）
- `vip_current_month_deposit` / `vip_current_month_turnover` / `vip_current_month_active_days`：當月累積（保級判斷用，月結後歸零重算）
- `vip_historical_max_level`：歷史最高等級（防重複領獎、決定「情境A首次晉升 / 情境B降級後重升」判斷用）
- `vip_retention_grace`：布林值，是否處於晉升當月保護期（D5）
- `vip_reward_claimed_levels`：已核發過一次性獎勵的等級清單（D4 防迴圈）

### D9. 保級「月活躍天數」定義
- **決定**：當日「有登入」且「該幣別有效投注 > 0」才算活躍一天
- **理由**：避免玩家只登入刷天數卻不玩，也避免自動化腳本掛機登入騙保級

### D10. 手動調級管控
- **決定**：三項管控都採用——(a) 強制填寫異動原因（必填，寫入稽核日誌）(b) 不影響玩家真實終生累積數據，只改「當前等級」與「歷史最高等級」(c) 管理員可選擇是否補發跨級的一次性晉級獎勵
- **理由**：異動原因必填是稽核基本要求；不動真實累積數據是為了避免人工調整污染晉升判斷的原始依據；補發獎勵設為可選給客服彈性處理個案（如跳過中間等級的補償性調整）

### D11. 特殊晉升條件
- **決定**：不支援任何「零儲值/零流水也能晉級」的特殊條件（如綁定手機號碼），所有等級一律只看儲值＋流水雙軌門檻
- **放棄方案**：沿用規格書 VIP2「綁定手機號碼」這類特殊晉升條件
- **理由**：Cooper 選擇簡化門檻邏輯的單一性，避免特殊條件與雙軌門檻並存造成判斷邏輯分支過多
- **影響**：這是本次設計與規格書新舊兩版最大的偏離之一，需要在對外文件中明確標註「與原規格書不同」，避免後續開發者誤查舊版規格

### D12. VIP 等級數量
- **決定**：維持 16 級（VIP0～VIP15），與規格書新版、現有程式碼一致

### D13. 門檻數值產生方式
- **決定**：由 Claude 先用數學模型（等比成長）推導一版草案，Cooper 之後逐級調整，不直接照抄規格書任何一版的數字
- **驗證方式**（依 CLAUDE.md 全域規則，金額類結論需附驗證方式，不可純人工推導）：
  1. 程式化檢查單調遞增、保級門檻低於晉升門檻，見 [vip_threshold_model.py](vip_threshold_model.py) 執行結果
  2. 用假設的 log-normal 分布模擬 20 萬名合成玩家的終生儲值/流水，帶入門檻算出各等級人數分布，作為「這套門檻切出來的等級分布長什麼樣子」的示意，**該模擬使用的玩家分布是假設值、非本平台真實數據**，僅供判斷草案數字的相對合理性，不是預測
- 詳細草案表與模擬結果見業務規格書 [docs/spec/vip-v2-spec.md](../spec/vip-v2-spec.md) 第 2.4 節，技術實作細節見 [docs/spec/vip-v2-tdd.md](../spec/vip-v2-tdd.md)

## 尚待討論（不在本輪決策範圍內）

- 週期性獎勵（零用金/生日禮/安慰金）是否要納入，以及各自的計算公式
- 門檻草案表的逐級數字最終定案（需要 Cooper 依實際玩家儲值/流水數據或營運目標調整）
- 是否需要 VIP 專屬客服、活動名額等非金錢類權益
